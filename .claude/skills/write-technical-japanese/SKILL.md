# 技術日本語ライティング

技術的事実を変えず、日本語話者の開発者が一度で理解できる文章を作る。技術分野を限定せず、セキュリティに関する文章にも同じ原則を適用する。

## ワークフロー

1. 依頼が新規作成、推敲、校正、要約、レビュー、翻訳後の自然化のどれに当たるかを特定する。
2. 対象リポジトリを参照できる場合は、表記規約、用語集、`CLAUDE.md`、`AGENTS.md`、`CONTRIBUTING`、近接する同種文書を確認する。文章作成に関係する規約だけを採用する。
3. 入力から、文書の目的、読者、掲載先、必須情報、希望する長さと形式、完成条件を特定する。
4. 結果を左右する情報が不足している場合は、完成稿を書き始めず、「不足情報の確認」に従って質問する。
5. 情報が揃ったら、[語彙例データセット](references/word-examples.md)を読み、事実を固定したまま構成と文章を整える。
6. 語彙例を候補として使い、文脈、読者、ユーザー指定、リポジトリ規約に合う語を選ぶ。語彙例へ機械的に置換しない。
7. 「最終確認」を行ってから出力する。

## 不足情報の確認

不足している項目だけを、1回につき3〜5問にまとめて質問する。単に「詳細を教えてください」と聞かず、回答が文章へどう反映されるか分かる具体的な問いにする。選択肢または短い回答例を添えられる場合は添える。

次の観点から、依頼ごとに必要なものを選ぶ。

- 文書と掲載先: 「公開リポジトリの README、社内の設計書、GitHub の PR 説明のどれですか」のように、媒体を特定する。
- 目的: 「読み手に仕様を理解してもらう、判断を求める、作業を実行してもらう、記録を残すのどれですか」のように、期待する行動を特定する。
- 読者: 役割、前提知識、対象システムへの関与、社内外の別を特定する。
- 必須情報: 残す数値、識別子、制約、結論、リンク、コード、未確定事項を具体的に確認する。
- 長さと形式: 文字数、Markdown、段落、箇条書き、表、コメント形式など、成果物の制約を確認する。
- 文体と用語: 既定値以外の文体、用語集、禁止表現、表記上の指定があるかを確認する。
- 完成条件: そのまま公開できる完成稿が必要か、レビュー用の草案か、修正理由も必要かを確認する。

依頼だけで必要情報が明確な項目は質問しない。「お任せ」と明示された項目には既定値を使う。回答を得られない技術情報が残る場合は、創作せず、ユーザーの同意を得て `要確認` と明示してから進める。

## 規約と指示の競合

ユーザーの明示指示とリポジトリの規約が競合した場合は、どちらかを推測で選ばない。競合する規則と文章への影響を短く示し、リポジトリの表記へ統一するかをユーザーに質問する。回答を得るまで、競合箇所を含む完成稿を作らない。

競合がなく、適用可能なリポジトリ規約がある場合はその規約を使う。規約がない部分だけ、本スキルの既定値を使う。

## 調査と事実の境界

文章作成に必要な外部調査や最新情報の検証を、このスキルだけでは行わない。ユーザーが提供した事実と参照可能な対象文書だけを材料にする。調査を求められた場合は別の調査手段が必要であることを伝え、調査結果を受け取ってから文章化する。

新規作成では、与えられていない数値、仕様、原因、影響、時系列、検証結果、出典を補わない。推敲では、次の要素を厳格に保つ。

- 数値、日時、単位、バージョン、固有名詞
- CVE、CWE、識別子、ホスト名、IP アドレス、ファイルパス
- URL、メールアドレス、コマンド、設定値、API 名
- コードブロック、インラインコード、ログ、エラーメッセージ
- 事実と推測の区別、可能性や確度、断定の強さ
- 原文が示す因果関係、条件、例外、否定

明白に誤って見える情報も勝手に訂正しない。完成稿とは別に疑義を示し、修正の可否を確認する。要約を明示的に依頼された場合は指定された範囲で情報を省けるが、残した事実の意味、条件、確度を変えない。

## 構成

事実と意図を保てる範囲で、見出し、段落、文、箇条書きの順序や粒度を組み替える。読み手が「何が起きたか」「なぜ必要か」「何をするか」を追える順序にする。

- 並列する項目は箇条書きにし、比較軸が揃う情報だけを表にする。
- 手順は実行順に並べ、前提条件を操作より前に置く。
- 結論や依頼事項を不必要な前置きの後ろに隠さない。
- 見出しは必要な階層だけにし、注記や括弧を増やしすぎない。
- 文書タイトルを含むすべてのヘッダは、名詞または名詞句で終える。
- 固定テンプレートやリポジトリ規約とヘッダの体言止めが競合する場合は、「規約と指示の競合」に従って質問する。
- 元の構成を維持する指定がある場合は、文と段落の範囲だけを直す。

## 日本語の書き方

指定がなければ「です・ます調」を使い、文書内で統一する。ユーザーが「である調」などを明示した場合は、その指定に従う。

- 一文では一つの主要な論点を扱う。条件や例外が多い場合は文を分ける。
- 主体が曖昧になる場合は主語を示し、明らかな場合は機械的に繰り返さない。
- 抽象名詞を重ねず、誰が何をするかを動詞で示す。
- 「〜することが可能です」は、意味が変わらなければ「〜できます」にする。
- 「以下では〜を説明します」のような内容のない予告、空疎な強調、同じ結論の反復を避ける。
- 専門用語を一般語へ勝手に言い換えない。同じ概念には同じ用語を使う。
- 公式の製品名、UI 名、英語の技術用語、略語の表記を保つ。必要な場合だけ初出で正式名称や短い説明を加える。
- 読者の前提知識にない用語は、精度を落とさない短い説明で補う。

## 語彙例の適用

- [語彙例データセット](references/word-examples.md)を、技術関連の名詞と動詞の選択、接続関係、確度の表現、冗長表現の修正に使う。
- データセットを必須語や禁止語の一覧として扱わない。文脈に合わない語は使わず、入力の技術用語やリポジトリの用語を優先する。
- 同じ概念には同じ語を割り当てる。同義語を文章の変化だけを目的に使い分けない。
- 原文の確度、因果関係、時制、主体を変える語へ置換しない。
- 技術用語を具体化する際も、入力にない処理順、データフロー、制御条件、回数の解釈、対象範囲を補わない。候補によって仕様の意味が変わる場合は、元の表現を保つか「不足情報の確認」に従って質問する。
- 参照元の文章を再現せず、語彙と用法だけを成果物の目的に合わせて利用する。

## 具体例と強調

- 成果物の具体例は、抽象的な説明だけでは理解が難しい場合に限って使う。
- 一つの論点につき具体例は最大1件とし、同じ内容の類似例を並べない。説明だけで伝わる場合は例を加えない。
- 入力に同じ結論を補足する例が複数ある場合も、最も代表的な1件だけを残す。例として書かれていても、別々の仕様、影響、検証結果を示す情報は削らず、具体例ではなく技術情報として整理する。
- 太字、斜体、下線、強調目的の全大文字、感嘆符、装飾記号を使わない。
- 「非常に」「極めて」「特に重要です」など、根拠なく重要性や深刻さを演出する語句を使わない。
- 推敲時は、原文の強調書式と不要な誇張を除去する。ただし、コード、ログ、引用原文、正式名称、入力で根拠が示された重要度や深刻度は変更しない。
- ユーザーが強調を明示的に指定した場合だけ、指定された範囲で使用する。

## 既定の表記

リポジトリ規約やユーザー指定がない部分に、次を適用する。

- 句読点は「、。」を使う。
- 英数字とASCII記号は半角を使う。
- 日本語と、英単語・英語の略語・英語表記の製品名が隣接する境界には、半角スペースを1つ入れる。
- 例: `APIを利用します` は `API を利用します`、`これはAPIです` は `これは API です` にする。
- URL、パス、コード、コマンド、識別子、メールアドレス、バージョン文字列は空白規則で変更しない。
- コードブロック、インラインコード、ログ、引用中の原文は変更しない。
- 行頭・行末や、句読点・括弧と英語の境界には余分な空白を入れない。例: `（API）を利用します`、`対象は API。` のままにする。
- 数字と日本語の境界には、この規則だけを理由に空白を加えない。

## 機微情報

入力と完成稿に、次の情報が含まれる可能性がないか確認する。

- API キー、アクセストークン、パスワード、秘密鍵、Cookie、セッション値
- 氏名、住所、電話番号、メールアドレスなどの個人情報
- 顧客名、顧客データ、契約や案件を特定できる情報
- 内部ホスト名、内部 IP アドレス、非公開 URL、非公開識別子
- 文書中で「機密」「社外秘」などと指定された情報

検知しても値を伏字化・削除・変更せず、周囲の文章を通常どおり整える。出力の最後に `## 機微情報に関する警告` を追加し、該当する入力行、見出し、段落などの位置と情報カテゴリを示す。警告内では値を再掲しない。たとえば「入力3行目: 認証情報の可能性があります。共有範囲を確認してください」と記す。該当しない場合は警告を追加しない。

## 出力

新規作成では、そのまま利用できる完成稿を最初に出す。ユーザーの同意を得て未確定事項を残した場合だけ、完成稿の後に `要確認事項` を示す。

推敲・校正では、次の順で出す。

1. `## 修正文` に、コピーして使える全文を示す。
2. `## 主な変更点` に、意味のある変更と理由だけを短く示す。
3. 機微情報を検知した場合は、最後に警告を示す。

ユーザーが見出しなし、本文のみ、差分形式などを明示した場合は、その形式を優先する。ただし、機微情報の警告は必ず最後に残す。

## 最終確認

出力前に次を確認する。

- 目的、読者、掲載先に合っているか。
- 必須情報を落としていないか。新しい事実を加えていないか。
- 数値、識別子、コード、ログ、リンク、確度を変えていないか。
- 文体と用語が統一されているか。
- 日本語と英語の空白規則を、例外を壊さず適用したか。
- 各ヘッダが名詞または名詞句で終わっているか。
- 具体例が理解に必要であり、一つの論点につき最大1件に収まっているか。
- 明示指定のない強調書式、感嘆符、装飾、根拠のない誇張が残っていないか。
- 冗長な前置き、反復、過剰な見出しや箇条書きがないか。
- 機微情報がある場合、位置を示す警告を最後に置いたか。
