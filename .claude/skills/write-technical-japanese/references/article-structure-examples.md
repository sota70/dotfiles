## 利用方針

セキュリティ記事を新規作成する場合、または見出しの新設・削除や章順の変更を伴う再構成をする場合に使う。構成例は固定テンプレートではない。文書の目的、読者、掲載先、ユーザ指定、リポジトリ規約に応じて、不要な節を省き、必要な節だけを使う。

各骨子の `{対象}`、`{問題}`、`{手法}` などは、入力で確認できる情報に置き換える。構成を埋めるために、入力にない影響、成立条件、検証結果、対策、時系列を補わない。情報が不足している節は省くか、ユーザの同意を得て `要確認` と示す。

主となる構成は一つにする。文書の目的に必要な場合だけ、別の構成から任意の節を取り入れる。見出し名は役割を示す例であり、そのまま使う必要はない。

## 種類の選択

題材ではなく、読者に求める行動で選ぶ。

| 読者に求める行動 | 主となる構成 |
| --- | --- |
| 自分の実装や設定を確認し、必要に応じて修正する | 開発者向け注意喚起 |
| 攻撃手法の原理、成立条件、検証方法を理解する | 攻撃テクニックの紹介 |
| CTF 問題の解法を追い、同じ結果を再現する | CTF writeup |

たとえば、CTF で発見した手法を一般的な攻撃テクニックとして説明する記事は「攻撃テクニックの紹介」を選ぶ。CTF の問題設定と解法の再現が主目的であれば「CTF writeup」を選ぶ。

## 開発者向け注意喚起

実装や設定に潜む問題を説明し、開発者が該当有無を判断して対処できるようにする記事へ使う。

### 構成の流れ

概要と対象読者 → 前提知識 → 問題の仕組み → 該当条件と影響 → コードベースの事例 → ベンダ対応 → 対策と確認方法 → 行動喚起

### 注釈付き骨子

1. `# {機能または製品}における{問題}`
   - 問題の対象と性質が分かるタイトルにする。
   - 深刻さや影響範囲を、根拠なくタイトルで断定しない。
2. `## 概要`
   - 何が問題で、誰が確認すべきかを冒頭で示す。
   - 記事で扱う事例、対象範囲、読後に期待する行動を短く示す。
3. `## 検証上の注意`（任意）
   - 攻撃コードや再現手順を含み、許可された環境での検証を明示する必要がある場合に置く。
4. `## {機能または技術}の前提`
   - 問題の理解に必要な仕様、データモデル、権限モデルだけを説明する。
   - 一般的な入門説明を広げず、後続の原因と影響につながる前提へ絞る。
5. `## {問題}の仕組み`
   - 正常な処理と問題が生じる処理の差を示す。
   - 入力、変換、判定、出力のどこで想定が崩れるかを明確にする。
6. `## 該当条件と影響`
   - 攻撃者が制御できる入力、必要な権限や設定、影響を受ける版などの成立条件を列挙する。
   - 影響を受けない条件も確認できる場合は併記する。
   - 成立可能性と実証済みの影響を区別する。
7. `## {実装または製品}の事例`
   - 対象コード、処理の流れ、問題が起きる入力、処理後の状態、影響の順に示す。
   - 複数事例がある場合は、各事例を同じ順序で説明して比較しやすくする。
8. `## ベンダ対応`（任意）
   - 報告先、回答、修正版、公開判断など、確認できた対応だけを時系列で示す。
   - ベンダの判断と筆者の評価を混同しない。
9. `## 対策と確認方法`
   - 更新、設定変更、入力検証、権限縮小などを、適用条件とともに示す。
   - 修正後に何を確認すればよいかを、コード、設定、テストの観点で示す。
10. `## まとめ`
    - 問題の原因、該当条件、開発者が取る行動を短く再掲する。
    - 本文で示していない新しい影響や対策を加えない。

### 構成上の注意

- 「脆弱な挙動」と「安全でない設定の組み合わせ」を分け、どの条件で影響が成立するかを示す。
- API やライブラリの内部処理を扱う場合は、呼び出し順に追い、問題が発生する箇所を特定する。
- コード例の直後に、そのコードから読み取れる事実と影響を説明する。
- 同じ対策を事例ごとに反復せず、事例固有の対策と共通の確認事項を分ける。

## 攻撃テクニックの紹介

攻撃手法の原理と成立条件を説明し、読者が検証方法、適用範囲、防御方法を理解できるようにする記事へ使う。

### 構成の流れ

手法の概要 → 成立原理 → 前提条件 → 最小 PoC → 実環境での発見過程 → 段階的な攻撃手順 → 完成した攻撃フロー → 適用範囲と制約 → 推奨対策

### 注釈付き骨子

1. `# {手法}による{結果}`
   - 手法と、実証または想定する結果を示す。
   - 限定された実装でのみ成立する場合は、一般化したタイトルを避ける。
2. `## 手法の概要`
   - 何を操作し、どの解釈差や挙動を利用し、何が可能になるかを短く示す。
   - 既存研究との関係や、本記事で新たに扱う点があれば示す。
3. `## 成立原理`
   - ブラウザ、プロトコル、サーバ、フレームワークなど、関係する各主体の解釈を分けて説明する。
   - 入力が各主体でどう変換されるかを、処理順に示す。
4. `## 前提条件`
   - 攻撃者が制御できる値、必要な脆弱性、対象実装、同一オリジンや Cookie などの条件を列挙する。
   - 必須条件と、攻撃を容易にするだけの条件を分ける。
5. `## 最小 PoC`
   - 原理を確認できる最小の入力と出力を示す。
   - コードや通信例の前後に、注目すべき値と期待結果を明記する。
6. `## 実環境の事例`（任意）
   - 実例がある場合に、入口となる弱点、利用できる機能、制御の回避、最終的な影響の順で示す。
   - 対象を特定できないように加工した情報は、加工した事実を明示する。
7. `## 攻撃手順`
   - 各段階を、目的、操作、観察結果の順に説明する。
   - 前段の結果が次段の前提になる箇所では、依存関係を示す。
8. `## 攻撃フローの統合`
   - 各段階を実行順にまとめ、最終 PoC または exploit を示す。
   - 完成コードだけでは分からない制約や調整値を補足する。
9. `## 適用範囲と制約`
   - 影響する実装やバージョン、ブラウザ差、既定設定、再現できなかった条件を示す。
   - 検証範囲を超えた対象へ結論を広げない。
10. `## 推奨対策`
    - 問題の原因へ対応する防御策を優先する。
    - 回避策しか示せない場合は、その制限と残るリスクを明記する。

### 構成上の注意

- 手法の一般原理と、特定環境で成立した攻撃チェーンを分ける。
- 「利用できる可能性」と「実際に窃取、回避、実行できたこと」を区別する。
- 特殊なパーサ、レガシー仕様、Cookie の順序など、成立に不可欠な細部を省かない。
- 攻撃コードを掲載する場合も、各処理が必要な理由を本文で先に説明する。

## CTF writeup

CTF 問題の制約、観察、推論、解法を示し、読者が同じ結果を再現できるようにする記事へ使う。

### 構成の流れ

問題情報と目標 → アプリケーション概要 → 制約と初期観察 → 解法の各段階 → 各段階の検証結果 → exploit の統合 → 実行結果 → 別解と応用例 → 結論

### 注釈付き骨子

1. `# {大会名}: {問題名} writeup`
   - 大会名、問題名、カテゴリなど、問題を識別できる情報を示す。
2. `## 問題情報`
   - カテゴリ、難易度、得点、solve 数、配布物、ソースコードなど、記事に必要なメタデータをまとめる。
   - 作問者 writeup の場合はその立場を示す。
3. `## 問題の概要`
   - 対象アプリケーション、攻撃者が利用できる機能、達成すべき目標を示す。
   - 関連するコードは、解法に必要な箇所へ絞って提示する。
4. `## 制約と初期観察`
   - 典型的な解法を妨げる制約と、レスポンス、状態、時間差などから観察できる情報を整理する。
   - この段階で未確認の内容を解法として断定しない。
5. `## 解法`
   - 解法を依存関係に沿った複数の段階へ分ける。
   - 各段階を「観察」「推論」「操作」「確認結果」の順で説明する。
6. `### 段階1: {利用する挙動}`
   - 最初の差分や primitive を特定し、単独で再現できる最小例を示す。
7. `### 段階2: {差分の増幅または変換}`
   - 前段の結果を、外部から観測できる状態へ変換する方法を示す。
8. `### 段階3: {観測方法}`
   - オラクルや判定方法を示し、真偽それぞれの期待結果を比較する。
9. `### exploit の統合`
   - 各段階の役割を短く再掲してから、完全な exploit を示す。
   - 調整値、試行回数、環境依存の処理がある場合は、その根拠を示す。
10. `## 実行結果`
    - 実行コマンド、主要なログ、取得した結果を示す。
    - 長いログは、成功を確認できる部分だけを残す。
11. `## 別解と応用例`（任意）
    - 意図解との違い、別解、類似問題への適用可能性を示す。
    - 問題外への一般化は、確認できた範囲と推測を分ける。
12. `## 結論`
    - 解法の核となる観察と、複数の挙動をどう接続したかをまとめる。

### 構成上の注意

- 最終 exploit を先に示さず、各部品が必要になった根拠を順に説明する。
- 試行錯誤をすべて時系列で残さず、解法の理解に必要な観察と失敗だけを選ぶ。
- コードの全体を掲載する前に、解法に関係する箇所を抜き出して説明する。
- flag、秘密値、接続先などの公開可否を確認し、機微情報に関する規則を適用する。
